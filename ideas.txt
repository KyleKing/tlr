TLR usability notes, from building the Cycle 52 standup sheet (2026-08-21)

Context: used tlr to prepare a 30-minute standup off Linear Cycle 52, added the `standup`
command, and hand-wrote STANDUP-C52-2026-08-21.md. Notes are ordered by how much time each
one cost or would save. Everything here was hit for real, not imagined.


1. No markdown output anywhere. This was the whole job and tlr did none of it.

   The CLI emits JSON, `export` emits SVG of the board. The deliverable was a document with
   tables. I hand-wrote every table in the sheet from JSON I read myself, which was most of
   the session's effort, and hand-copying numbers is exactly where transcription errors come
   from (I made five and had to correct them).

   `standup --format md` emitting the roll-up, hop, and capacity tables would have collapsed
   that. Same for capacity, timeline, and forecast. The JSON stays the default so it still
   pipes.


2. `--out` on standup duplicates OOO machinery tlr already has. My fault, worth undoing.

   capacity.people[person].cycles[n] already carries outDays, oncall, and reason, fed by the
   gcal and incident.io refresh tasks, and personCycleCapacity() already deflates for both.
   src/commands/capacity.ts uses it correctly.

   standup ignores all of that: it recomputes per-person velocity from completed points and
   takes a manual comma-separated --out list. So there are now two sources of capacity truth
   and the newer one is the dumber one. It should call personCycleCapacity() like capacity.ts
   does, keep the completed-points average only as the velocity input, and treat --out as an
   override for someone the calendar does not know about yet.


3. `data-sample.json` is the default --project for nine commands and does not exist.

   Every bare `deno task cli capacity` (or scan, timeline, balance, forecast, plan, review,
   export, standup) fails on a missing file. web/data has pr2026.json, seed-a.json,
   seed-b.json, horse-tinder.json, cpu.json, and no data-sample.json.

   Better: default to the sole entry in projects.json when there is exactly one, otherwise
   fail naming what is actually available.


4. `snapshots` is in the CLI usage text but missing from the README's command list.

   I did not know it existed, so I went at web/data/tlr.sqlite with raw sqlite, wrote a
   query that counted table definitions instead of rows, and told Kyle the store held one
   capture. It held 126, spanning a month, from a cron that had been running fine unattended.
   I had to correct that out loud.

   One README line prevents a wrong conclusion reaching the user. The lesson is broader than
   this command: an undocumented read path pushes people to the database, and hand-rolled
   SQL against someone else's schema is where confident wrong answers come from.


5. Unestimated tickets are handled four different ways.

   balance warns and leaves them unscheduled. timeline counts them. capacity, forecast,
   diff, and export silently fold them in as 0.

   On the real workspace this is not a rounding error: 32 of 62 unfiled tickets carried no
   estimate, so every points total in the sheet is a floor by an unknown margin. Any command
   that emits a points number should emit the unestimated count beside it, so a reader can
   tell "45 points" from "45 points plus fourteen unknowns". standup does this now; the
   others should.


6. Snapshot accumulation is not the only source of history, and tlr assumes it is.

   The architecture treats "diff two captures" as the way to know anything over time, which
   is why I assumed cycle-hop counts would need weeks of snapshots before they meant
   anything. Wrong: Linear's issue history exposes fromCycle/toCycle per issue, complete and
   retroactive. cyclePath got a correct ten-hop path (DEV-7725, 43 through 52) on the very
   first ingest with zero accumulation.

   The same is true of assignee, estimate, and state changes. Worth amending adr/0006: read
   from Linear's history where Linear records it, and spend snapshots on what it genuinely
   does not, which is milestone scope over time. That is still a real gap and still the best
   argument for the snapshot store, just a narrower one than the current framing claims.


7. Project-scoped store cannot answer a team question. (Now written up in ROADMAP.)

   A standup covers a team; the snapshot store is keyed per project, so tlr sees only
   Product Reliability 2026. Every number it reports for that project is right, but the
   roll-up groups by milestone instead of project, and work with no project cannot appear at
   all. That last part is the expensive half: unfiled tickets were 29% of open scope and the
   single largest block on the board, and tlr is structurally blind to them.


8. Hop paths outrun the cycles array.

   Ingest keeps the last 12 cycles. DEV-6012's path starts at cycle 28 and runs
   28>29>30>51>57>51>52>53. Anything that renders a path against known cycle windows will
   have holes, and the 51>57>51 segment shows paths are not monotonic, so a UI cannot assume
   left-to-right time.


9. "Every command prints JSON, so it pipes cleanly" is not quite true through `deno task`.

   The task banner means `deno task cli standup ... | python3` needs 2>/dev/null. I hit this
   and misread it as malformed output. The compiled dist/tlr binary avoids it, so either
   point the README examples at that or note the redirect.


10. Roster resolution degrades quietly.

    The refresh printed "24 assignees, 0 resolved, 1 unresolved (left blank): Adrian Dinu".
    A contractor on a personal gmail never resolves, so anything keyed on roster email drops
    them silently. Adrian holds 16 points of unfiled work, so dropping him is not harmless.
    An unresolved assignee should be a visible flag on the board, not one line of refresh log.


What worked well, so it does not get changed by accident:

- The snapshot cron ran for a month unattended, 126 captures, current to the hour, no
  babysitting. It also correctly skipped horse-tinder.json as belonging to another
  workspace instead of failing the run.
- `deno task issues` picked up the new history field and refreshed 159 issues first try.
- The pure-module layout meant `standup` was one file in src/commands plus a CLI case, and
  7 tests covered it without a fixture or a mock.
- The Issue contract making cyclePath optional (undefined, not empty) is what let old
  captures report "unknown" rather than "zero hops". Keep that distinction, it is load
  bearing for any field added later.
